讨论 MCP 时，必须区分三个问题：模型为什么决定调用工具，客户端如何发现并调用服务能力，以及消息怎么在两个进程之间传输。Tool Calling、MCP 和 stdio / HTTP 分别处在不同层，不能互相替代。

这篇文章以 **MCP 2025-11-25 版传输规范**为讨论基线，不是对未来版本的兼容承诺。该版列出的标准传输是 stdio 与 Streamable HTTP；2024-11-05 版的 HTTP+SSE 是需要单独识别的旧方案。具体实现应核对双方 SDK 和协商版本。[版本化传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

## 先把模型与服务分开

```text
模型提出工具调用建议
        ↓
Agent 应用：参数、权限、审批和执行策略
        ↓
MCP Client：协议交互与能力调用
        ↓  stdio 或 HTTP
MCP Server：工具、资源等能力的实现
```

Server 提供了删除文件的工具，不意味着模型获得了无限制删除权限。应用侧的授权和服务侧的校验仍然必要。传输协议解决的是互通，不是所有业务安全问题。

同样，只有几个固定函数的小应用不一定需要 MCP。是否拆成独立 Server，取决于复用、部署和维护需求，而不是工具数量达到某个神奇阈值。

## stdio：客户端管理的子进程

stdio 模式下，客户端启动 Server 子进程，通过标准输入发送消息，通过标准输出读取消息。消息是按换行分隔的 UTF-8 JSON-RPC，协议输出中不能混入普通日志。

最容易忽视的问题不是网络，而是启动行为：

- 子进程能否找到解释器、依赖和工作目录。
- 需要哪些环境变量，是否误继承了不必要的凭据。
- 退出、异常和重启时，客户端如何收集日志并清理资源。
- Server 是否在启动时向 stdout 打印了欢迎语。

例如 Python 的下面片段只演示**日志通道**，不构成完整 MCP Server：

```python
import logging
import sys

logging.basicConfig(stream=sys.stderr, level=logging.INFO)
logging.info("server initialized")
```

stderr 出现内容并不必然代表启动失败，普通诊断日志也可以写到这里。判断成败还要结合进程退出码、协议初始化结果和调用响应。

stdio 经常用于本地工具，但“没有监听端口”不等于“自动沙箱”。子进程仍然可能读取文件、访问网络或使用继承的环境变量，需要限制文件范围和运行权限。

## 旧式 SSE 不等于当前 HTTP 方案

SSE 是服务端向客户端发送事件的一种 HTTP 流机制。它既能出现在旧式 MCP HTTP+SSE 中，也能作为 Streamable HTTP 的响应形式，因此不能只看到 `text/event-stream` 就判定是哪一种 MCP 传输。

| 方案 | 交互组织 | 容易误解的地方 |
| --- | --- | --- |
| stdio | 子进程 stdin / stdout | 把 stdout 当日志输出 |
| 旧 HTTP+SSE | SSE 接收通道与消息提交入口 | 认为所有 SSE 都属于旧方案 |
| Streamable HTTP | 同一 MCP 端点处理 POST / GET | 认为响应必须一直是 SSE |

在本文选定的规范中，Streamable HTTP 的 POST 请求用于提交 JSON-RPC 消息，客户端声明接受 JSON 与 SSE；服务端对请求可返回 JSON 或事件流。GET 可以用于打开服务端事件流，也可能不被支持。它不是“把旧 SSE 路由改一个名字”。

旅行应用向浏览器推送执行进度的 SSE，又是另一条业务链路。浏览器展示任务进度与 MCP Client 调工具，即使都使用 HTTP，也不因此成为同一个协议。

## 会话与协议版本不能靠 URL 猜

实现应完成 MCP 初始化与版本协商，再按规范发送后续请求。支持会话的服务端可以返回 `MCP-Session-Id`；客户端要按约定维护它，而不是拿自己的聊天 ID 随意替代。

`MCP-Protocol-Version` 表达后续 HTTP 请求使用的协议版本。聊天记录、身份令牌和 MCP 会话标识承担不同职责，混用会造成权限与生命周期错误。

排查时可以分别记录：协议版本、请求 ID、会话是否存在、HTTP 状态和耗时。不要把令牌、完整凭据或带敏感参数的地址写进日志。

## 断线不意味着调用没有发生

网络断开后，客户端可能没有收到结果，但工具的写入动作已经完成。若直接重发“创建订单”或“删除对象”，就可能执行两次。

因此我会按工具性质设计重试：只读查询可以在明确条件下有限重试；有副作用的操作则需要业务幂等键、结果查询或人工确认。恢复事件流与重做业务动作不是一回事，JSON-RPC 请求 ID 本身也不能替代业务幂等性。

stdio 进程崩溃同样会产生这个问题。不能因为通信发生在本机，就忽略“执行完成但响应丢失”的中间状态。

## 本地和远程服务的安全检查

规范要求 HTTP 服务校验 Origin，以降低 DNS rebinding 风险；本地服务应优先只绑定回环地址，并实施适合场景的认证。需要远程连接时，应另外设计身份、传输保护、限流和权限范围，而不是直接暴露开发服务。

我的最小排查顺序是：先看启动与连接，再看协议初始化，再看能力发现，最后看具体工具参数与授权。如此可以避免把“Server 没启动”“协议不兼容”和“业务拒绝调用”全部归结为模型选错工具。

本文是协议与工程边界整理，没有声称已经完成某个 SDK 的互操作测试。接入时应使用对应版本的官方 SDK，并针对进程退出、超时、断线和重复调用做实际测试。
