HyDE 的核心不是让模型先回答一遍，再把这个回答当事实。它让模型生成一段**假想相关文档**，用这段文本的向量去寻找知识库中真正存在的文档。生成文本是检索中间产物，最终证据仍然必须来自可追溯的原始资料。

旅行问答很容易遇到表达不对齐：用户问“带老人去玩，怎么少走路”，知识库写的是“步行距离、无障碍设施、接驳车和坡度”。短问题没有覆盖文档里的完整概念，直接检索可能错过有用材料。这是我在整理 Agent 笔记时理解 HyDE 的切入点。

## 从问题向量到假想文档向量

普通向量检索与 HyDE 的主要差别在查询侧：

```text
普通检索：问题 → 编码器 → 查询向量 → 真实文档

HyDE：问题 → 生成假想相关文档 → 编码器
                                  ↓
                            文档库近邻搜索
                                  ↓
                           真实证据 → 回答
```

原论文把这一方法放在零样本稠密检索场景中，使用生成模型提供文档式表达，再由对比学习编码器建立检索表示。不能因此推导出“任何 LLM 搭配任何向量模型都一定有效”。具体实现和论文设定见 [HyDE 原论文](https://arxiv.org/abs/2212.10496)与[作者代码](https://github.com/texttron/hyde)。

例如，假想文本可以描述：“适合长者的路线应比较步行距离、休息点与接驳交通，并核对开放时间。”这只是帮助检索的主题表达。若文本进一步编出了某景区的电梯位置或票价，这些细节并没有获得事实地位。

## 和其他查询处理方法的区别

| 方法 | 产生什么 | 主要目的 |
| --- | --- | --- |
| 查询改写 | 更明确的问题 | 补全指代，保留已有条件 |
| 多查询检索 | 多个检索问题 | 从不同角度寻找候选证据 |
| HyDE | 假想相关文档 | 缩短查询与文档的表达距离 |
| 重排序 | 候选的相关性顺序 | 在已召回集合内重新选择 |

它们可以组合，但不要一次全部打开。否则效果变好或变差时，很难定位是哪一个环节造成的。先保留直接检索基线，再逐项引入，通常更容易解释实验。

如果问题只是省略了城市，首选是从会话状态补全城市，而不是让 HyDE 自己猜。缺失的是事实条件，不是表达方式。

## 一个不依赖具体 SDK 的处理边界

下面是流程伪代码，不是可直接调用的框架 API：

```text
输入：已经完成指代消解的问题、用户权限、知识库版本
1. 从问题提取必须保留的城市、日期和限制条件
2. 生成假想文档；禁止新增未经提供的业务条件
3. 对问题或假想文档编码，执行权限与时间过滤后的检索
4. 合并候选，按稳定文档 ID 去重
5. 重排，保留可核对的原文与来源
6. 只把真实证据送入回答阶段
7. 证据不足则说明不足，不把假想文本补成事实
```

“禁止新增条件”的提示词只能降低风险，不能成为安全保证。应用仍需检查必需约束、限制生成长度，并把假想文本与真实证据保存成不同字段。日志中也应明确区分 `hypothesis` 与 `retrieved_evidence`，方便复查。

可以同时保留原问题检索这一分支，降低假想文档偏离主题的风险。但混合结果如何融合、取多少候选，仍需实验决定，不能直接把所有结果塞进上下文。

## 哪些场景不应该优先用 HyDE

精确编号、错误码、函数名和订单号通常更适合关键词或精确匹配。生成长段落反而可能把最有用的检索锚点稀释掉。

实时价格、库存与订单状态也不能靠 HyDE 解决。它可以找到接口说明，却无法把过期知识变成实时数据。真正的状态仍需通过已授权工具查询。

此外，以下情况应先解决基础链路：

- 文档未入库或被错误切分：查询扩展无法召回不存在的证据。
- 权限过滤有缺陷：相关性提升不等于权限正确。
- 用户问题有多个合理含义：先澄清，比围绕错误假设扩展更可靠。
- 延迟预算很紧：新增生成调用需要计算真实成本。

## 怎么证明它改善了检索

我会建立一组固定问题，给每题标注真正相关的文档 ID，至少分出短问题、精确实体问题、多条件问题和无答案问题。相同语料、切块、编码器与候选预算下，比较直接检索和 HyDE。

检索侧看 Recall@K、排序指标与错误召回类型；系统侧看生成调用成本、端到端延迟和超时；回答侧再看引用是否支持结论。只看最终回答“更像样”，可能把语言润色误当成检索改善。

如果保留原问题分支后总候选数变多，也应额外比较一个候选预算相近的基线，避免把“拿了更多资料”误判为 HyDE 本身有效。

本篇没有给出本地实验提升百分比。我的工程结论是：HyDE 是一个需要对照评测的查询侧选项，不是 RAG 的必选组件，更不是绕过证据不足的捷径。
