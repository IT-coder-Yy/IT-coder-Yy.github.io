Agent 页面重新连上服务器，不代表它补齐了断线期间的事件。文本增量、已保存消息和执行状态具有不同生命周期：恢复连接只是传输问题，恢复界面与任务需要独立的数据契约。

## 先区分三种数据

| 数据 | 用途 | 典型恢复策略 |
| --- | --- | --- |
| 文本增量 | 即时展示生成过程 | 临时缓存或最终消息替换 |
| 完整消息 | 重新打开会话 | 按会话读取持久历史 |
| 执行事件 | 工具状态、阶段与产物更新 | 事件游标回放或状态快照 |

不是所有 Token 都必须永久保存。如果最终消息已持久化，可以在恢复时替换临时文本；但开始执行、工具完成和任务结束等状态事件，需要有可恢复依据。

## SSE 和 WebSocket 只解决部分问题

标准 EventSource 可以在事件包含 `id` 时维护最后事件 ID，并在重连时发送 `Last-Event-ID`。服务端仍需决定如何解释游标、保存哪些事件以及如何回放。[HTML SSE 标准](https://html.spec.whatwg.org/multipage/server-sent-events.html)

用 `fetch` 自己读取 SSE 格式，并不自动获得 EventSource 的全部重连行为。WebSocket 的连接与消息帧也不定义应用层事件历史恢复，需要自行约定游标和确认机制。[WebSocket 协议](https://www.rfc-editor.org/rfc/rfc6455)

两种传输都不能仅凭连接成功保证业务上的不重不漏或“恰好一次”。

## 事件需要稳定游标

教学用事件可以包含流 ID、单调序号、事件类型和实体版本。

```json
{
  "stream_id": "example-run",
  "sequence": 42,
  "type": "task.stage_changed",
  "entity_version": 7,
  "payload": {"stage": "rendering"}
}
```

序号的意义必须明确：是整个流有序，还是某个实体有序？如果有多个独立流，客户端应分别保存游标，不能把一条流的序号用作另一条流的进度。

事件先持久化，再由实时推送层通知客户端。若状态更新与事件写入分离，应处理一致性窗口；可参考事务性 Outbox，同时保留消费者去重。[Outbox 模式](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## 回放与实时切换不能留空窗

一种设计是在一致性边界内取得高水位，并注册高水位之后的有界实时缓冲；回放游标到高水位的历史后，再消费缓冲中的后续事件。另一种设计让消费端始终从持久日志按游标读取，实时通知只用于唤醒。

不应先查询历史、再注册订阅而没有任何补偿机制：两步之间产生的事件可能同时不在查询结果和订阅结果中。

客户端按流 ID 与序号去重，并只在事件成功应用后推进已应用游标。状态更新还需检查实体版本，避免重复事件或旧版本把界面退回过去。

## 慢消费者与过期历史

客户端处理速度落后时，无界队列会把一次网络问题变成服务器内存问题。缓冲应设上限，达到上限后断开并要求从持久历史恢复，或明确降级为状态快照。

历史有保留期限。游标早于最早事件时，服务端应返回需要重新同步的信号，客户端加载快照与对应游标，再继续消费后续事件；不能悄悄跳过缺口仍声称完整恢复。

## 重连必须重新检查权限

游标只是位置，不是访问许可。会话、任务和事件流都要绑定当前身份；权限被撤销后，重连不能因为持有旧序号就继续读数据。临时连接票据和签名链接应避免进入普通日志。

恢复测试应覆盖重连重复事件、回放期间产生新事件、事件应用失败、慢消费者、游标过期和权限变化。最后还要区分连接取消与任务取消：用户离开页面，不一定意味着服务端应取消已提交的长任务。
