视频处理通常包含识别、素材匹配、渲染和产物保存，耗时远长于一次普通 HTTP 请求。关键不是把函数移到后台，而是在进程退出、响应丢失或回调重复之后，仍能判断任务已经完成到哪一步。

## 接收与完成使用不同语义

创建接口先校验输入、持久化任务，再返回任务 ID 和状态查询入口。HTTP `202 Accepted` 表示请求被接受处理，不代表处理已经完成或一定成功。[RFC 9110 的 202 定义](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

如果任务数据和队列消息分别写入不同系统，要处理两者之间的失败窗口：任务已保存却没有消息，或消息已发出但任务事务回滚。可通过事务性 Outbox 保存待发送事件，并由发送器重试投递。[Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

## 阶段状态必须能解释恢复动作

```text
queued → recognizing → matching → rendering → saving → succeeded
                       ↓              ↓
                  waiting_remote / reconciling
任意可执行阶段 → failed 或 cancelled
```

阶段名称是教学示意。持久记录应包含输入摘要、配置快照、当前阶段、外部任务 ID、截止时间、尝试次数和结果引用。不能只保存一个“正在执行”的布尔值。

临时签名 URL 不适合作为唯一恢复依据。保存稳定的媒体身份与必要元数据，在恢复时重新取得访问链接。

## 领取任务需要原子边界

多个 worker 不能只靠进程内集合避免重复领取。任务领取与状态变更需要数据库原子操作、队列确认机制或租约等设计，并在并发更新时检查当前阶段或版本。

租约过期不代表旧 worker 已经停下。涉及写入时，还需通过版本条件或 fencing token 拒绝过期执行者的更新，并让外部副作用具备幂等或对账能力。

FastAPI 的 `BackgroundTasks` 适合响应后的进程内工作，并不自动提供跨进程任务领取或重启恢复。重计算、多进程和多服务器任务需要单独的执行系统。[FastAPI 后台任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/#caveat)

## 回调与轮询可以到达同一终态

等待远端结果时，回调减少等待，轮询可作为恢复与补偿路径。两者都应调用同一个条件式状态更新：只有任务仍处于对应等待阶段，且远端身份和尝试版本匹配，才允许写入终态。

重复回调返回稳定结果；迟到的旧尝试不能覆盖新尝试；成功终态不能被后续超时检查改成失败。回调还应按双方约定验证身份、签名与重放条件，不能只相信正文中的任务 ID。

截止时间要持久化。恢复后使用剩余预算，而不是从头重新计算一整段超时，否则多次重启会让任务无限等待。

## 提交超时是结果未知

向渲染服务提交后发生网络超时，可能是请求没有送达，也可能是服务已经创建任务、只是响应丢失。盲目重提会造成重复渲染或计费。

优先使用远端幂等键、调用方请求 ID 或状态查询来对账。没有这些能力时，应明确保存不确定状态，并限制自动补偿，而不是宣称端到端“恰好一次”。Outbox 能解决本地事务与消息投递的一类一致性问题，但消费者仍需处理重复消息。

## 恢复测试比正常流程更重要

在持久化后未投递、远端接收后未回写、回调重复、轮询与回调同时完成、保存产物中断等位置注入失败。检查任务不会丢失、重复副作用可识别、终态不倒退、过期 worker 无法覆盖结果。

前端可以展示阶段进度，但“完成百分比”应来自可解释的工作量或阶段定义，不能把任意等待时间包装成精确进度。
