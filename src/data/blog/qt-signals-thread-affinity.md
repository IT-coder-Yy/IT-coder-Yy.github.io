信号槽提供了跨线程通信方式，但不会让所有调用自动变安全。理解它要同时回答：对象属于哪个线程，信号从哪个线程发出，以及连接类型决定槽在哪个线程执行。

在视频应用里，后台负责采集和推理，主线程负责界面。仅仅把一个对象命名为 Worker，或者把连接写成 `connect`，都不能证明工作已经离开 UI 线程。

## QObject 归属与 QThread 对象不是一回事

QObject 通常属于创建它的线程；满足条件时可以通过 `moveToThread` 调整归属。父子对象要遵守线程归属约束，已有 parent 的对象不能随意搬到另一个线程。

QThread 对象本身通常仍属于创建它的线程，`run()` 才在新线程执行。因此，把业务槽直接写进 QThread 子类，并不意味着这些槽天然运行在新线程。Worker 对象模式可以让这种归属关系更清楚。[Qt 官方线程与 QObject 说明](https://doc.qt.io/qt-6/threads-qobject.html)

```text
主线程：Window / Controller / QThread 对象
                      ↓ 启动
工作线程：Worker 对象 + 工作线程事件循环
                      ↓ 结果信号
主线程：窗口槽函数更新 UI
```

注意，普通 C++ 成员函数调用 `worker->doWork()` 不经过排队机制。调用来自主线程时，函数就在主线程执行，不会因为 worker 的归属自动切线程。

## 三种连接的执行位置

| 连接类型 | 槽执行方式 | 执行线程 |
| --- | --- | --- |
| DirectConnection | 发信号时立即调用 | 发射信号的当前线程 |
| QueuedConnection | 进入接收方事件队列 | 接收对象归属的线程 |
| AutoConnection | 发射时判断是否同线程 | 同线程直接，否则排队 |

Auto 的判断比较的是**当前发射线程**与接收方归属，不只是发送对象与接收对象的归属。这个细节能解释许多“对象明明在另一个线程，为什么槽没有排队”的困惑。

Queued Connection 需要接收线程有能够继续运行的事件循环。如果槽里执行一个永不返回的循环，后续排队消息也可能一直没有机会被处理。

BlockingQueuedConnection 还会阻塞发射线程，同线程使用会死锁，跨线程也可能与锁等待形成环。不要把它当作解决所有时序问题的快捷方式。

## UI 更新保留在主线程

QWidget 及其子类应在主线程使用。后台可以计算结果或生成独立图像数据，通过排队连接交给窗口槽处理；不要在工作线程直接调用控件的 `setText`、修改布局或操作窗口。

下面是 **Qt 6 集成片段**，假定 `worker`、`window` 已经创建，`Worker::frameReady` 与 `Window::showFrame` 是兼容的信号和槽。它不是包含采集与窗口代码的独立程序：

```cpp
QObject::connect(worker, &Worker::frameReady,
                 window, &Window::showFrame,
                 Qt::QueuedConnection);
```

带上下文对象的连接会随接收上下文销毁而断开，但这不意味着其他后台资源已经安全停止。窗口生命周期和工作线程生命周期还需要明确协调。

## 图像跨线程传递要表达所有权

即使槽在正确线程执行，图像数据也可能已经被复用。cv::Mat 拷贝通常共享缓冲；包装外部采集缓冲的 QImage 也可能依赖外部内存。排队传递一个对象，并不自动获得底层像素的独立副本。

我会明确选择以下一种契约：

- 发射前生成独立快照，接收方持有它。
- 使用带所有权的不可变共享缓冲，保证直到所有消费者结束才复用。
- 明确移动交接，并保证生产者不再修改已经交出的数据。

自定义参数类型还应满足 Qt 元对象系统和排队连接的要求。具体注册方式需结合连接方式与 Qt 版本核对，不能忽略运行时关于无法排队参数的警告。

帧率高时，还要限制待显示结果数量。每一帧都排队，即使每个槽执行都安全，也可能让 UI 持续显示旧画面。

## 为什么 stop 槽有时不起作用

如果工作槽正在一个长循环里持续读帧，排队的 stop 槽需要等事件循环恢复才能执行。`quit()` 请求退出事件循环，也不能自动终止当前阻塞的读操作。

一种办法是把工作拆成能返回事件循环的小步任务；另一种是让工作循环检查线程安全的停止状态或 `isInterruptionRequested()`，并为网络读、条件变量等待等阻塞点设置退出机制。

`requestInterruption()` 只是协作请求，不会强制终止线程或自动取消 I/O。[QThread 中断说明](https://doc.qt.io/qt-6/qthread.html#requestInterruption)

因此停止顺序应考虑：请求停止、解除或限时等待阻塞、停止生产与消费、释放设备和解码资源、确认线程结束，再销毁仍被引用的对象。不要只看停止标志已经变为 true。

## 生命周期与测试清单

Qt 文档展示了把线程 `finished` 与 Worker 的 `deleteLater` 连接的模式。它解决对象清理的一部分，但使用时仍需核对 parent、线程是否结束，以及其他线程是否还持有对象引用。

在调试版本中可以记录发射点、槽入口的线程标识和对象的 `thread()`，验证实际执行位置；不要凭日志先后顺序推断线程归属。
