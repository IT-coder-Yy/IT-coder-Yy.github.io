当任务需要“查多页数据、过滤记录、按组统计，再返回少量结果”时，每查一页都让模型重新决定下一步，往往增加上下文和往返成本。程序化工具编排把这部分控制流交给代码，但模型生成的程序仍然是不可信输入，权限和停止条件必须由应用拥有。

## 从逐次调用到程序控制流

普通工具调用通常返回一个工具名和参数，应用执行后把观察交回模型。程序化编排则允许一个程序组合多个受控工具，并在运行时完成循环、条件判断和聚合。

CodeAct 论文研究的是以可执行代码表达 Agent 动作，并利用执行反馈继续修正；具体产品中的程序化工具调用，是这种思路的一类工程实现，不能仅凭名称断言两者有相同运行环境或安全保证。[CodeAct 论文](https://arxiv.org/abs/2402.01030)

一次查询就能解决的问题，使用普通工具调用更直接。只有控制流和中间数据真的复杂时，额外运行时才可能抵消它带来的维护成本。

## 模型与执行器的责任

```text
模型生成程序
  → 输入与预算检查
  → 隔离运行时
  → 受控工具代理 → 外部服务
  → 有界结果与错误摘要
  → 模型修正或结束
```

模型负责提出操作；运行时负责计算、资源限制和结束；工具代理负责认证、授权与真实副作用。不能因为代码通过语法检查，就允许它访问任意文件、网络或凭据。

固定一个结果出口，例如 JSON 可序列化的 `result`，可以减少日志、中间变量与正式输出混杂。结果仍要限制大小、校验结构并检查敏感字段，不能直接把整个进程输出写回上下文。

## 聚合留在运行时

下面是 Python 3 标准库示例。`pages` 是合成数据，用于演示分页结果聚合，不包含真实 API 调用，也不是沙箱实现。

```python
from collections import Counter

pages = [
    [{"group": "A", "status": "ready"},
     {"group": "B", "status": "pending"}],
    [{"group": "A", "status": "ready"},
     {"group": "B", "status": "ready"}],
]

counts = Counter()
for page in pages:
    counts.update(row["group"] for row in page
                  if row["status"] == "ready")

result = dict(sorted(counts.items()))
assert result == {"A": 2, "B": 1}
```

真实分页还需限制页数、记录数和总时长，识别重复游标，并明确数据是否来自同一快照。否则“代码执行成功”可能只代表统计了一个不断变化的数据集合。

## 错误反馈不等于无限重试

字段名错误、输出结构不符等局部问题，可以反馈脱敏错误类型和可用字段，让模型在总预算内修正。权限拒绝不能靠换参数绕过；外部提交超时则可能已经产生副作用，应先对账，而不是直接重新执行整个程序。

可审计记录包括程序哈希、工具调用、参数摘要、结果状态和消耗，不要求记录模型的隐藏推理。每次修复都应有新的可验证变化，重复程序或无进展循环应停止。

## 语言限制与安全隔离

RestrictedPython 可以约束部分语言行为，但其官方文档明确说明它不是沙箱或安全环境。[RestrictedPython 文档](https://restrictedpython.readthedocs.io/en/latest/)

对不可信代码，需要独立评估进程或虚拟化隔离、CPU 与内存上限、执行超时、文件系统、网络出口和系统调用。容器也不是自动安全的：高权限挂载、宿主凭据和开放出口都可能破坏边界。长效密钥应留在工具代理，而不是进入代码运行环境。

## 用任务结果评估编排收益

比较相同任务集上的完成率、模型轮数、实际工具调用数、输入输出 Token、总延迟和失败恢复率。工具调用数不能被“一个执行工具”掩盖：程序内部的请求同样产生费用和副作用。

程序化编排的价值，是在可验证、可停止的边界内处理控制流和数据，而不是赋予模型一个无限能力的 Python 解释器。
