ViBe 用每个像素的一组背景样本来判断当前观测是否接近背景。它检测的是变化，不直接判断“这是气体”“这是人”或“这是危险”。在红外视频中，它可以提供疑似变化区域，但语义与告警还需要额外证据。

本篇根据背景建模笔记重组，算法依据是 Barnich 与 Van Droogenbroeck 的 [2011 年 ViBe 论文](https://orbi.uliege.be/handle/2268/145853)。下面的 NumPy 代码仅演示分类，不冒充完整实现或实际设备性能测试。

## 每个像素不只保存一个背景值

若只保存一个背景灰度，树叶摆动或传感器噪声就容易导致频繁前景判断。ViBe 为位置 `x` 保存 N 个样本，当前值与这些样本逐一比较。

```text
位置 x 的背景模型：[v1, v2, ... , vN]
          当前值：v
          ↓
统计距离小于 R 的样本数
          ↓
达到 min_matches → 背景
否则             → 前景
```

这里的样本是历史和邻域更新形成的观测值，不是 N 个独立类别。实际实现可以在达到匹配数后提前停止，不必每次都遍历全部样本。

初始化可从首帧邻域抽取样本，利用局部相似性快速建立模型。如果首帧里存在静止目标，它也可能被视为背景。启动速度快不意味着初始化没有偏差。

## 随机更新与邻域传播

原始方法对判为背景的像素进行概率性更新：有机会随机替换自身模型中的一个样本，也有机会将当前观测写入邻居的模型。这使历史样本具有不同的存活时间，并将局部背景信息传播到附近。

随机更新不是“每隔固定若干帧更新一次”。固定周期与概率抽样有不同的时间行为。更新概率越大，通常适应变化越快，也可能更容易把不该适应的变化吸收到模型；参数不能只追求一帧掩码干净。

只对判为背景的当前像素发起更新，也不能绝对保证目标永远不被吸收：误分类和邻域传播都可能改变模型。停止运动的目标、缓慢变化区域与初始鬼影，仍然需要单独观察。

## 可运行的灰度分类示例

以下 Python 3 + NumPy 示例支持 uint8 或 uint16 灰度帧。采用严格的 `distance < radius` 判定，只输出 0 / 255 掩码；不包含初始化、随机替换与邻域更新。

```python
import numpy as np


def classify_gray(frame, samples, radius, min_matches=2):
    if frame.ndim != 2 or samples.ndim != 3:
        raise ValueError("需要 H×W 帧和 H×W×N 样本")
    if samples.shape[:2] != frame.shape:
        raise ValueError("帧和背景模型尺寸不一致")
    if frame.dtype not in (np.dtype("uint8"), np.dtype("uint16")):
        raise ValueError("只支持 uint8 / uint16")
    if samples.dtype != frame.dtype:
        raise ValueError("帧与样本必须使用相同数据类型")
    if radius <= 0 or not 1 <= min_matches <= samples.shape[2]:
        raise ValueError("距离阈值或匹配数不合法")

    delta = np.abs(
        samples.astype(np.int32) - frame[..., None].astype(np.int32)
    )
    background = (delta < radius).sum(axis=2) >= min_matches
    return np.where(background, 0, 255).astype(np.uint8)


frame = np.array([[10, 200]], dtype=np.uint8)
samples = np.array([[[9, 11, 12], [10, 11, 12]]], dtype=np.uint8)
print(classify_gray(frame, samples, radius=5))  # [[  0 255]]
```

必须先转成能容纳有符号差值的类型。直接对 uint8 做减法，负数可能绕回较大的正数，造成错误距离。uint16 的完整差值同样可以被这里的 int32 容纳。

这段向量化实现会创建 `H×W×N` 的中间数组，适合验证逻辑，不适合直接作为高分辨率多路视频的性能结论。背景样本本身的内存约为 `H×W×N×每样本字节数`，还未包含掩码与计算临时数据。部署时可考虑逐行处理、提前结束匹配和缓冲复用。

## 红外显示归一化会影响背景距离

同一块物理背景，在逐帧独立归一化后的 8-bit 图像里可能改变灰度。若每帧都重新拉伸最小最大值，模型看到的变化既可能来自场景，也可能来自显示映射。

因此我会保持算法输入的映射规则一致：优先在适合算法的数据域建模，或者使用稳定的显示映射，并根据该数据域设定阈值。把一个 8-bit 视频的距离参数直接搬到 uint16 原始数据上，没有可靠依据。

## 失败场景比单帧效果更重要

| 场景 | 可能的表现 | 检查方向 |
| --- | --- | --- |
| 相机抖动 | 大片边缘成为前景 | 固定相机、配准或其他模型 |
| 全局亮度变化 | 大范围前景 | 输入映射、变化检测与重建策略 |
| 慢速或静止目标 | 逐渐融入背景 | 更新行为与任务定义 |
| 高频噪声 | 零散点反复出现 | 数据域、距离阈值与去噪 |
| 首帧有目标 | 鬼影或目标漏检 | 初始化与后续适应过程 |

形态学开闭运算和面积过滤能够改善掩码可读性，但也可能删除真正的小目标。尤其是弱对比度、半透明区域，不能把“噪点少了”直接当成“检测更准了”。

如果用掩码裁剪后再运行深度模型，应保留掩码漏检的评测。候选区域节省了计算，也可能让后续模型再也看不到真实目标。

## 验证和使用边界

我会保存同一段视频的原始帧、模型参数和掩码，检查稳定背景、目标进入、目标停留、目标离开和相机移动这些时段。需要告警时，再评估误报、漏报和触发延迟，不能只看处理 FPS。

算法作者提供了[原始项目与实现说明](https://www.telecom.ulg.ac.be/research/vibe/)。集成第三方实现前应阅读对应许可证与使用条件；本文的小示例不表示获得了原始实现的商用授权，也不对专利状态作判断。

我的结论是：ViBe 是可解释的变化检测基线。它适合帮助定位候选前景，但不能替代场景定义、设备数据确认和语义检测评测。
