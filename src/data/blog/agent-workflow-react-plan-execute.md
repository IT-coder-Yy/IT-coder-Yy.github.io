很多系统只要“调用了模型和工具”就被称为 Agent，结果是设计评审时大家使用同一个词，却讨论四种完全不同的执行方式。真正有用的区分标准不是宣传名称，而是：谁决定下一步、状态存在哪里、失败后如何收敛。

## 普通模型调用与 Agent 的边界

普通模型调用通常是：应用准备消息，模型生成一次输出，应用返回结果。即使这次输出使用了结构化 JSON，也不必然构成 Agent。

Agent 至少增加了一个由状态驱动的执行循环：模型或策略根据当前目标和观察选择行动，应用执行工具，把结果写回状态，再决定继续、重试、改计划或结束。

```text
目标 → 状态 → 选择行动 → 执行工具 → 观察结果 → 更新状态
          ↑                                  ↓
          └──────── 继续 / 停止条件 ──────────┘
```

关键变化不是“模型更聪明”，而是系统允许模型影响后续执行。因此权限、超时、最大步数和审计也必须进入架构。

## Workflow：路径由代码拥有

Workflow 的节点和主要路径由开发者提前定义。模型可以参与分类、抽取或生成，但它不能随意跳出图中允许的边。

例如一个技术资料核验流程可以固定为：

```text
接收主题 → 搜索官方来源 → 提取版本 → 交叉检查 → 生成摘要 → 人工确认
```

如果搜索失败，代码进入重试或“证据不足”分支。它的优势是容易测试、审计和预测成本；缺点是难以覆盖大量开放任务。

Anthropic 将 workflow 描述为由预定义代码路径编排模型与工具的系统，并建议从最简单的方案开始，只在复杂性确实带来价值时增加自主性。[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)

## ReAct：行动与观察交替

ReAct 的核心不是把隐藏推理过程展示给用户，而是让模型在任务执行中交替产生任务相关行动，并用环境返回的观察更新后续决策。

原始论文将 reasoning traces 与 task-specific actions 交错使用，使模型能够根据外部环境信息调整计划。[ReAct 论文](https://arxiv.org/abs/2210.03629)

工程中可以把可审计部分表示为：

```text
选择 search_docs(query)
→ 观察：找到 3 个官方页面
→ 选择 read_page(url)
→ 观察：版本条件不一致
→ 选择 read_release_notes(version)
→ 观察：条件得到确认
→ 输出结论与来源
```

它适合路径无法完全预定义、工具集合受控且每一步都能获得新证据的任务。主要风险是循环调用、工具误选、步骤过长和成本失控。

## Plan-Execute：先建立全局结构

Plan-Execute 先生成可检查的任务计划，再由执行器逐步完成。它解决的是长任务缺少全局结构的问题，而不是保证计划永远正确。

```text
目标
→ 生成计划 [核对版本、复现实例、检查失败边界、整理来源]
→ 执行当前步骤
→ 校验结果
→ 必要时重规划
→ 汇总
```

如果计划生成后不可更新，任何外部变化都会让后续步骤建立在旧假设上。因此工程实现通常需要：步骤状态、依赖关系、完成标准、重规划入口和总预算。

## 四种方式放在同一张表里

| 方式 | 下一步由谁决定 | 状态 | 优势 | 主要风险 |
| --- | --- | --- | --- | --- |
| 普通模型调用 | 应用固定 | 消息与一次响应 | 简单、低成本 | 无法执行长任务 |
| Workflow | 代码路径 | 工作流状态 | 可预测、易测试 | 开放任务覆盖有限 |
| ReAct | 模型在允许动作中选择 | 行动与观察历史 | 灵活、能利用新证据 | 循环、误调用、成本 |
| Plan-Execute | 计划器与执行器共同决定 | 计划、步骤和结果 | 长任务结构清晰 | 旧计划、重规划复杂 |

这些方式不是互斥产品。一个系统可以在不同层级同时使用它们。

## 为什么常用“外层 Workflow、局部 Agent”

确定性流程适合控制关键边界，自主循环适合处理局部不确定性。组合时可以这样分工：

1. 外层 Workflow 固定入口、权限、预算、审核和结束条件。
2. 计划节点把开放目标拆成可验证步骤。
3. 某个资料搜索步骤允许 ReAct 在白名单工具中迭代。
4. 工具结果必须通过结构与业务校验后才能写回状态。
5. 最终发布仍由确定性检查或人工确认控制。

这种结构不是为了“多用一种架构”，而是把灵活性限制在它真正有价值的局部。

## 让循环能够停止

无论 ReAct 还是 Plan-Execute，都需要代码级停止条件：

- 最大总步数和单工具调用次数；
- 单次工具超时与任务总超时；
- 相同工具、参数和结果摘要的重复检测；
- 无新证据时停止继续搜索；
- 工具白名单与参数范围；
- 失败后返回已完成部分和缺失信息；
- 高风险操作必须人工确认。

停止条件不是 Prompt 建议，而应由执行器强制。否则模型只要继续请求工具，系统就可能持续消耗资源。

## 如何选型

先问三个问题：

1. 路径是否可以提前写清？可以就优先 Workflow。
2. 每一步是否会获得改变下一步的新证据？会，再考虑 ReAct。
3. 任务是否长到需要先管理依赖与完成状态？是，再加入 Plan-Execute。

如果一次模型调用已经能稳定完成，不要为了叫作 Agent 引入执行循环。工程目标是可控地完成任务，而不是最大化自主性。
