RAG 回答错误时，先不要只修改最后的提示词。正确证据可能没有进入知识库，也可能在切块、召回、排序或上下文组装时丢失。只有证据已经进入模型输入，才值得重点检查模型是否误读。

原始 RAG 研究讨论了检索与生成结合的方法；实际业务里还需要加入解析、过滤、引用和评测等工程环节。下面的链路是我的工程拆解，并非对原论文架构的逐项复刻。[RAG 原论文](https://arxiv.org/abs/2005.11401)

## 把离线和在线链路分开

```text
离线：原始文档 → 解析 → 切块与元数据 → 编码 → 索引

在线：问题 → 条件补全与权限过滤 → 候选召回
     → 去重与重排 → 上下文预算选择 → 带证据回答
```

每个块应能返回原文位置、文档 ID 和版本。只有一段向量而没有来源，回答即使正确也很难复核。

切块不是越短越好：定义与例外条件可能被拆开，表格列名可能离开单元格。也不是越长越好：多个主题挤在一个块里，相关片段会被噪声掩盖。我会按文档结构切分，再检查实际问题能否在一个或相邻几个块中找到完整证据。

## 相似度不等于业务正确性

余弦相似度使用点积除以两个向量的模长乘积：

```text
cosine(a, b) = dot(a, b) / (norm(a) * norm(b))
```

它不是“欧氏距离除以模长”。当向量已经做单位归一化时，点积与余弦相似度数值一致；欧氏距离仍是距离指标，排序方向和数值含义不同。零向量没有定义良好的余弦值，应用应检查异常输入。

同样，随便取一个语言模型的 CLS 或平均池化输出，不意味着获得了适合检索的表示。要核对编码器的训练目标、query / document 用法、归一化和距离配置，并用目标语料测试。

城市、时间、文档权限这类条件不应只依赖向量“理解”。旅行问答先限制到目标城市和有效日期，再比较语义相关性，通常更容易解释错误来源。

## 召回与重排分别负责什么

召回面对整个文档集合，强调用可接受的成本找出候选；重排面对较小候选集，进一步判断问题与文档的相关性。Bi-Encoder 可以预先编码文档；Cross-Encoder 联合处理问题与候选，适合作为二阶段排序器。[Sentence Transformers 官方检索与重排说明](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)

重排不能把候选集之外的证据凭空找回来。若正确文档根本没有进入候选，优先检查切块、过滤和召回，而不是一直更换 Reranker。

可以把候选数量和最终上下文数量分别记作 `candidate_k` 与 `context_k`。两者没有通用固定值：前者影响漏召回和重排成本，后者受上下文预算、文档冗余与证据完整性约束。

模型的原始相关性分数也不一定是概率。阈值应在具体模型和语料上校准，不应把一个系统的 0.5 搬到另一个系统。

## 两个可运行的检索指标

以下 Python 3 示例只用标准库，采用二值相关文档标注。排名列表必须先按文档 ID 去重；无相关文档的题目不纳入这两个指标，应另测无答案处理。

```python
def retrieval_metrics(ranked, relevant, k):
    if k <= 0 or not relevant:
        raise ValueError("k 必须为正，且相关集合不能为空")
    if len(set(ranked)) != len(ranked):
        raise ValueError("排名列表必须先去重")

    top = ranked[:k]
    recall = len(set(top) & relevant) / len(relevant)
    reciprocal_rank = next(
        (1.0 / rank for rank, doc in enumerate(top, 1)
         if doc in relevant),
        0.0,
    )
    return recall, reciprocal_rank


recall, rr = retrieval_metrics(
    ["doc-c", "doc-a", "doc-d"], {"doc-a", "doc-b"}, 3
)
print(recall, rr)  # 0.5 0.5
```

Recall@K 看前 K 个结果覆盖了多少已标注相关文档；单题 RR@K 看第一个相关文档的排名倒数，未命中为零。对多题 RR 取平均才是 MRR@K。

同样的 Recall，相关文档排在第一和排在最后，对有限上下文的生成阶段可能差别很大。需要多证据支撑的问题还应检查证据集合是否齐全，不能只奖励第一个相关块。

## 按阶段做错误分析

| 检查位置 | 观察到的现象 | 优先检查 |
| --- | --- | --- |
| 原始资料 | 根本没有对应事实 | 增补资料或承认无答案 |
| 文档块 | 原文有，但块里不完整 | 解析与切块边界 |
| 候选集 | 正确块未出现 | 过滤、编码、检索和候选预算 |
| 重排结果 | 正确块被挤到后面 | 排序模型与截断长度 |
| 模型上下文 | 选中的块没被注入 | 去重、预算与拼接 |
| 最终回答 | 有证据但结论错误 | 证据理解、冲突处理与引用 |

评测集应包含短查询、精确实体、多条件、过期资料和无答案题。保留相同的数据版本，记录召回和重排参数，再比较准确性、延迟及成本。不要拿不同语料或不同候选预算的结果直接宣称某个模型更好。

## 有引用仍然可能答错

引用存在不代表引用支持结论。可以逐条检查回答中的事实，确认原文是否真正表达了该事实、时间是否一致，以及是否把条件性的建议写成绝对承诺。

对于需要实时价格或库存的问题，文档检索不能替代实时工具。证据不足时明确说明范围，比继续扩大 Top-K 并让模型猜测更可靠。

本文的数字示例仅用于验证指标计算，不是旅行知识库的实验成绩。先建立可复查的基线和错误分类，再讨论换模型，才能让优化有证据。
