RTSP 是会话控制协议，FFmpeg 是处理音视频的工具与库。它们不是同一层的两种替代方案：应用可以通过 RTSP 建立会话，再使用 FFmpeg 读取、解封装并解码压缩视频，最终获得能交给图像算法的像素数据。

但不能反过来说“所有红外相机都输出 H.264”。工业相机也可能通过 SDK 提供原始高位深帧。先确认设备输出格式，再选择数据链路，才能避免把已经丢失的信息当作原始测量值。

## 一帧图像经过哪些环节

```text
网络相机
  → RTSP 会话控制
  → RTP 等媒体传输（可使用 UDP 或 TCP 交织）
  → 解封装：提取压缩包
  → 解码：压缩包变成像素帧
  → 像素格式转换
  → 显示 / 图像处理 / 模型输入
```

FFmpeg 的 libavformat 负责输入与解封装，libavcodec 负责解码，libswscale 常用于像素格式和尺寸转换。一个压缩包不一定恰好对应一帧；某些编码结构还会带来重排序与缓冲。

在 FFmpeg 中，RTSP 作为 demuxer / muxer 使用。这里讨论的是从相机拉流的 demuxer 方向，不是把相机地址当作普通本地文件。[FFmpeg 官方 RTSP 说明](https://ffmpeg.org/ffmpeg-protocols.html#rtsp)

OpenCV 的 VideoCapture 也可能使用 FFmpeg 等后端，所以“OpenCV 完全不能读压缩流”不准确。直接使用 FFmpeg 库的价值在于可以更明确地控制选项、错误处理、帧时间戳和资源生命周期，而不是工具名称本身保证稳定性。

## 先用命令行分离网络与应用问题

下面适用于已安装 FFmpeg / ffprobe 的 Windows PowerShell。先在当前会话中设置 `RTSP_URL` 环境变量，值使用你有权访问的设备地址；不要把真实凭据写进文章、仓库或截图。

```powershell
if (-not $env:RTSP_URL) {
    throw '请先设置当前会话的 RTSP_URL'
}

ffprobe -hide_banner -rtsp_transport tcp -timeout 5000000 `
    -select_streams v:0 -show_streams -of json "$env:RTSP_URL"

ffmpeg -hide_banner -rtsp_transport tcp -timeout 5000000 `
    -i "$env:RTSP_URL" -t 10 -an -f null -
```

第一条观察视频流的编码、分辨率与像素格式；第二条尝试解码十秒并丢弃输出，不创建录像文件。输入选项放在 `-i` 前；这里的 `timeout` 是 RTSP TCP I/O 超时，单位为微秒，因此示例是五秒，不是五百万秒。

环境变量只是避免把地址硬编码到脚本，不能保证凭据不出现在进程参数或工具日志中。分享日志之前仍需脱敏，使用测试账号时也应限制权限。

FFmpeg 的不同发行版可能有选项差异。可以先运行以下命令核对本机支持情况，而不是遇到报错就随意替换参数：

```powershell
ffmpeg -version
ffmpeg -hide_banner -h demuxer=rtsp
```

本文命令已按官方选项核对，但没有可访问的测试相机，因此不宣称完成了真实设备拉流验证。

## TCP 与 UDP 不能只比较“谁更快”

UDP 不做 TCP 式可靠重传，但应用仍要处理丢包、乱序和缓冲；TCP 可以降低部分网络环境中的连接困难，丢包重传也可能阻塞后续数据，增加延迟。

选择时应使用同一个设备和同一段网络做对照，观察首帧时间、丢帧、画面破损、重连与帧龄。不能因为 TCP 在一次测试中连接成功，就认定它在所有低延迟场景中最优。

减少探测或缓冲也有代价：可能更快进入画面，却识别不完整或更容易丢失数据。先获得稳定基线，再逐项修改参数，并保存参数与版本。

## 从解码帧到算法输入的所有权

FFmpeg 的 send / receive 解码接口需要处理“继续送包”和“继续取帧”的状态，不能假定调用一次就一定得到一帧。处理结束时还要根据场景刷新解码器并释放资源。[libavcodec 解码接口文档](https://ffmpeg.org/doxygen/trunk/group__lavc__encdec.html)

AVFrame 的数据可能带有行跨度，也不一定是连续的 RGB。转成 cv::Mat 或 QImage 时，要核对像素格式、每行字节数和生命周期。如果只包装解码缓冲区后马上复用 AVFrame，另一个线程就可能读到已经被覆盖的数据。

我的接口约定会明确：帧是独立拥有缓冲区，还是带引用计数共享；允许谁修改；入队后何时释放。只写“传一个 Mat”不足以表达这些边界。

## 断流、卡顿与重连分别处理

| 现象 | 先观察什么 | 常见定位方向 |
| --- | --- | --- |
| 连接失败 | 地址、认证、网络、错误码 | 会话与网络层 |
| 有压缩包但没有画面 | 编码信息、解码返回值 | 编码支持或解码状态 |
| 画面越来越旧 | 队列长度、帧龄、处理耗时 | 消费速度不足 |
| 长时间卡在读操作 | 超时与中断机制 | 网络阻塞 |
| 频繁重连 | 断流原因与重连间隔 | 设备、网络或状态处理 |

实时预览与完整录像对丢帧的要求不同。预览可能只需要最新帧，录像则不能默默沿用同一丢弃策略。重连后还应清理旧帧，重建必要的解码状态，避免新旧会话数据混在一起。

重连使用有限重试和退避；用户主动停止后不再重连。阻塞读取要有超时或中断回调，仅设置一个布尔变量并不能让已经阻塞的网络调用立刻返回。

## 红外原始值与显示视频不能混为一谈

如果设备通过 SDK 输出 uint16 原始数据，算法分支应保留设备定义的有效位深、单位与标定关系。普通压缩预览视频即使来自同一相机，也可能已经经过显示映射和编码，不能自动恢复原始温度或辐射值。

因此我会分别验证原始采集链路和可视化链路。FFmpeg 可以解决视频接入问题，但不能替代设备 SDK、标定说明和对原始数据格式的确认。
